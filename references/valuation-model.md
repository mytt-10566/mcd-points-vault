# 估值模型与标准输入格式

## 标准输入 JSON

`scripts/points_vault.py` 接受如下结构。所有字段均可缺省，引擎会安全降级而不是报错。

```json
{
  "now": "2026-10-09",
  "account": {
    "available_points": 3260,
    "accumulated_points": 18400,
    "frozen_points": 0,
    "expiring": [
      { "points": 800, "expire_date": "2026-10-31" }
    ]
  },
  "mall_products": [
    {
      "name": "麦乐鸡 5 块兑换券",
      "points": 250,
      "cash_value": 13.5,
      "valid_days": 30,
      "kind": "餐品券"
    }
  ],
  "coupons": [
    {
      "name": "满 30 元减 8 元券",
      "cash_value": 8.0,
      "min_spend": 30,
      "expire_date": "2026-10-15"
    }
  ],
  "recent_redemptions": []
}
```

字段别名容忍：引擎接受 `points` / `amount` / `value` / `balance`、`expire_date` / `expiry` / `deadline` / `end_date`、`cash_value` / `value` / `market_price` / `reference_value` 等写法自由对应，便于直接喂入 MCP 原始返回值。日期支持 `YYYY-MM-DD`、`YYYYMMDD`、带时间戳等形式。

## 核心公式

| 指标 | 公式 | 含义 |
| --- | --- | --- |
| 每 100 积分兑现价值 | `cash_value / points × 100` | 全篇核心排序指标，越大越划算 |
| 积分最优汇率 | `max(上述指标)` | 现行最划算的兑换出口 |
| 积分账面价值 | `available_points × 最优汇率 / 100` | 积分折现总额 |
| 券面总值 | `Σ coupon.cash_value` | 券的合计面值 |
| **资产合计** | `积分账面价值 + 券面总值` | 报告抬头数字 |
| 风险敞口 | `Σ(30 天内到期的积分) × 最优汇率 / 100` | 不管就会蒸发掉的金额 |

### 为什么用「每 100 积分」而非「每积分」

每积分价值通常是 0.04~0.06 元的量级，可读性差；放大 100 倍后落在 4~6 元的直觉区间，用户一眼就能比较。

### 为什么用「最优汇率」折算积分

积分本身没有唯一市价，取决于你把它花在哪里。用当前所有可行兑换中的最高效率作为折算基准，得到的是「这笔积分理论上最多值多少」——这是对用户最有决策价值的口径：它同时告诉你资产上限和优化空间。

## 风险分档

| 剩余天数 | 等级 | 含义 |
| --- | --- | --- |
| `< 0` | 紧急 | 已过期作废 |
| `0 ~ 7` | 紧急 | 一周内，必须立刻处理 |
| `8 ~ 30` | 注意 | 一个月内，建议本周内安排 |
| `> 30` | 安全 | 从容处理 |

风险敞口统一按 30 天窗口统计。

## 建议兑换路径算法

对即将过期的积分，用贪心策略生成一份可执行清单：

1. 把所有可用积分商品按「每 100 积分兑现价值」降序排列。
2. 依次取用：若剩余待覆盖积分足够支付该项，则取 `⌊剩余 / 所需积分⌋` 个（至少 1 个）。
3. 扣减后继续下一项，直到剩余积分不足以支付任何商品。

选择贪心而非背包最优的理由：兑换商品是整数件、品类有限，贪心解与最优解的差距通常极小，而结果更容易向用户解释——「先换效率最高的，能换几个换几个」。过度优化反而降低可解释性。

若最终仍有积分无法覆盖，报告会显式提示「剩余 N 积分无法用现有商品覆盖」，并建议改走领券兜底，而不是假装问题已解决。

## 数据质量守则

- `cash_value` 无法获取时置 `0` 并在报告注明，**不编造价格**。
- 「即将过期积分」缺失时，明确告知用户数据不足，不推测。
- 所有估值均为参考值，报告中必须保留免责声明，商品、价格与库存以麦当劳官方渠道为准。
