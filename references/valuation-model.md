# 估值模型与标准输入格式

## 标准输入 JSON

`scripts/points_vault.py` 接受如下结构。所有字段均可缺省，引擎会安全降级而不是报错。

```json
{
  "now": "2026-10-09",
  "account": {
    "available_points": 2741.9,
    "accumulated_points": 7576.1,
    "frozen_points": 0,
    "expired_points": 1223.2,
    "expiring": [
      { "points": 129.8, "expire_date": "2026-10-31" }
    ]
  },
  "mall_products": [
    {
      "name": "16.9元麦辣可乐组合",
      "points": 500,
      "cash_value": 15.1,
      "kind": "到店专用",
      "note": "常规价 32.00 − 用券价 16.90"
    }
  ],
  "coupons": [
    {
      "name": "中薯条",
      "cash_value": 13.5,
      "min_spend": 0,
      "expire_date": "2026-12-31"
    }
  ],
  "recent_redemptions": []
}
```

**积分为小数**（麦享会积分实际就是 `2741.9` 这种字符串），引擎按浮点处理，不会截断。

字段别名容忍：引擎接受 `points` / `amount` / `value` / `balance`、`expire_date` / `expiry` / `deadline` / `end_date`、`cash_value` / `value` / `market_price` / `reference_value` 等写法自由对应，便于直接喂入 MCP 原始返回值。日期支持 `YYYY-MM-DD`、`YYYYMMDD`、带时间戳等形式。

> MCP 原始返回不能直接喂进本引擎，需要先经 `tools/normalize_mcp.py` 归一化（原因见上一节与 `MCP_INTEGRATION.md`）。

## 核心公式

| 指标 | 公式 | 含义 |
| --- | --- | --- |
| 单项净节省 | `常规价 − 用券价` | 兑换该项能真正少花多少钱 |
| 每 100 积分兑现价值 | `净节省 / points × 100` | 全篇核心排序指标，越大越划算 |
| 积分最优汇率 | `max(上述指标)` | 现行最划算的兑换出口 |
| 积分账面价值 | `available_points × 最优汇率 / 100` | 积分折现总额 |
| 券面总值 | `Σ coupon.cash_value` | 券的合计价值 |
| **资产合计** | `积分账面价值 + 券面总值` | 报告抬头数字 |
| 风险敞口 | `Σ(30 天内到期的积分) × 最优汇率 / 100` | 不管就会蒸发掉的金额 |

### ⚠️ 为什么「净节省」而不是「面值」

这是本项目最容易被做错、也最关键的一处口径。麦麦商城的积分兑换项**绝大多数不是面值券，而是「折扣购买权」**：

> 券面原文：凭本券可享受 **21.9 元购买**巨无霸可乐组合，含 1 份巨无霸 + 1 份中可乐。

花 800 积分换到的，是**以 ¥21.9 买下这个组合的权利**，不是一张 ¥21.9 的券。

- 若把 `extTradePrice`（21.9）直接当价值：`21.9 / 800 × 100 = 2.74 元/100分`
- 若按净节省算：常规价（巨无霸 25.5 + 中可乐 9.5 = 35.0）− 21.9 = **13.10**，`13.10 / 800 × 100 = 1.64 元/100分`

两者不仅数值不同，**排序结论也会被完全颠倒**。本引擎采用后者。

常规价的取数口径：`query-meals` 的 `originalPrice`（不参加优惠活动时的常规标价），这与麦当劳券面说明第 10 条「节省金额是与常规价格相比较」保持一致。

### 为什么用「每 100 积分」而非「每积分」

每积分价值通常是 0.02~0.03 元的量级，可读性差；放大 100 倍后落在 2~3 元的直觉区间，用户一眼就能比较。

### 为什么用「最优汇率」折算积分

积分本身没有唯一市价，取决于你把它花在哪里。用当前所有可行兑换中的最高效率作为折算基准，得到的是「这笔积分理论上最多值多少」——这是对用户最有决策价值的口径：它同时告诉你资产上限和优化空间。

### 为什么必须先验证在售状态

`mall-points-products` 会把已下架商品一并返回，且 `status` 字段无法区分（实测恒为 2）。若不逐个调 `mall-product-detail`，报价单里会混入大量**早已无法兑换的僵尸商品**，把「最优汇率」抬到一个根本不存在的水平。实测 24 个积分兑换项中 17 个已下架 —— 不做这一步，报告就是错的。

## 风险分档

| 剩余天数 | 等级 | 含义 |
| --- | --- | --- |
| `< 0` | 紧急 | 已过期作废 |
| `0 ~ 7` | 紧急 | 一周内，必须立刻处理 |
| `8 ~ 30` | 注意 | 一个月内，建议本周内安排 |
| `> 30` | 安全 | 从容处理 |

风险敞口统一按 30 天窗口统计。

## 建议兑换路径算法

对即将过期的积分，用贪心策略生成一份可执行清单：

1. 把所有可用积分商品按「每 100 积分兑现价值」降序排列。
2. 依次取用：若剩余待覆盖积分足够支付该项，则取 `⌊剩余 / 所需积分⌋` 个（至少 1 个）。
3. 扣减后继续下一项，直到剩余积分不足以支付任何商品。

选择贪心而非背包最优的理由：兑换商品是整数件、品类有限，贪心解与最优解的差距通常极小，而结果更容易向用户解释——「先换效率最高的，能换几个换几个」。过度优化反而降低可解释性。

若最终仍有积分无法覆盖，报告会显式提示「剩余 N 积分无法用现有商品覆盖」，并建议改走领券兜底，而不是假装问题已解决。

## 数据质量守则

- `cash_value` 无法获取时置 `0` 并在报告注明，**不编造价格**。
- 「即将过期积分」缺失时，明确告知用户数据不足，不推测。
- 所有估值均为参考值，报告中必须保留免责声明，商品、价格与库存以麦当劳官方渠道为准。
